## Context

The repository currently runs a Next-compatible App Router through `vinext` and Vite with the Cloudflare Vite plugin and Worker entry. The existing `next.config.ts` has no static-export configuration, there is no GitHub Actions workflow, and the current application routes combine server catalog loading, Next navigation, API calls, process-local repositories, cookies, and server-only configuration. The installed toolchain already includes Vite, React, and the React Vite plugin, so a separate static entry can be built without adding a dependency or changing the Worker build.

The completed visual foundation is the presentation authority. Existing Catalog/Product components are useful references, but several import `next/link` or are coupled to server/API boundaries; they cannot be imported wholesale into a static Vite entry. See `proposal.md` and `specs/github-pages-frontend-preview/spec.md` for the motivation and observable contract.

## Goals / Non-Goals

**Goals:**

- Produce one inspectable static frontend artifact that works at a GitHub repository subpath.
- Reuse the current FigMemento visual tokens, CSS, typography, public media behavior, and safe pure catalog/customization logic where the import graph is client-safe.
- Give stakeholders a deterministic, honest walkthrough of the storefront and the major local commerce/fulfillment screens.
- Make the preview build fail closed when it accidentally crosses into server authority or embeds a secret.
- Provide a manual Pages workflow and a concise human setup/runbook.

**Non-Goals:**

- Do not static-export the primary App Router or alter the vinext/Cloudflare Worker runtime.
- Do not reuse server-backed Cart, Checkout, Order, Payment, Fulfillment, CustomerUpload, Admin, Supabase, or provider integrations inside the artifact.
- Do not create fake server responses, durable browser state, fake credentials, private upload receipts, Orders, Payments, fulfillment actions, tracking records, or production deployment behavior.
- Do not change the active `build-local-fulfillment-runtime` or `build-local-tracking-runtime` planning artifacts, tasks, or semantics.

## Decisions

### 1. Use an isolated Vite/React preview entry

Create a preview-only entry under `preview/github-pages/` with a dedicated Vite configuration and a repository-root script that emits a known static output directory. The preview entry owns its HTML shell, client router, fixtures, demo state, and preview components. It may import approved CSS tokens, public asset references, and server-free pure domain/helper modules after an explicit import audit, but it must not import Next components, server modules, API route modules, or runtime configuration that reads secrets.

This is preferred over changing `next.config.ts` to force static export because the current App Router includes server-backed routes, cookies, dynamic data loading, and API authority. It also avoids making the production Worker architecture conditional on GitHub Pages.

### 2. Share the visual layer through CSS and pure contracts, not server-coupled components

The implementation will reuse the existing global visual tokens and storefront stylesheet authority where compatible, and will reuse pure catalog formatting/selection or customization validation helpers only after source inspection. Preview-specific components will provide navigation and data adapters without `next/link`, server fetches, or server repositories. If a current component cannot be isolated without importing server behavior, the implementation will create a small presentation adapter rather than weakening the source boundary or copy-pasting the whole application.

### 3. Use explicit static fixtures and a hash-based client router

Preview fixtures will live under the preview boundary and will contain only public presentation data: safe product/category/variant/customization examples, local asset references or controlled fallback metadata, and visual payment/fulfillment states. Client state is in memory and resets on reload. Routes use a base-aware entry path plus hash fragments such as `#/`, `#/shop`, `#/category/<slug>`, `#/product/<slug>`, `#/cart`, `#/checkout`, `#/order-success`, `#/payment`, `#/fulfillment`, and `#/operator`.

Hash routing is chosen over pretty static paths because GitHub Pages does not provide the application server's dynamic route fallback. It makes direct refresh deterministic without adding a 404 rewrite trick or claiming that a server route exists. The build base is supplied through a non-secret build value (for example the repository name in the workflow), while all in-preview links are generated by the router.

### 4. Model commerce and fulfillment as presentation state machines

The preview will use small client-only state machines for Cart, Checkout, Payment, and Fulfillment visuals. The state machines will use visibly labeled demo transitions and no network transport. A local image selection uses `URL.createObjectURL`/equivalent browser-local preview behavior with cleanup; it never calls the CustomerUpload route. Order Success uses a placeholder display reference and `Paid — Demo`, not the real Local Order route or a generated authority.

The Fulfillment visual sequence will cover Photo Review, preview v1, revision, v2, optional v3, approval, In Production, and Quality Check. Operator controls are visual-only and labeled `UI PREVIEW ONLY`; Tracking is omitted or labeled not implemented. This keeps the presentation useful without duplicating the canonical Local Fulfillment aggregate or selector semantics.

### 5. Use repository-local public assets and controlled fallback

The preview will use checked-in `public/` assets and safe local/catalog presentation data. It will not rely on `localhost`, signed URLs, private storage, remote image hosts, font CDNs, or provider proxies. When a desired product image is not available as a safe local asset, the existing public-media fallback style will be used rather than adding an external dependency or a fake private asset.

### 6. Deploy manually through a least-privilege Pages workflow

Apply will add a custom workflow with `workflow_dispatch` as the initial trigger. It will install from the lockfile, build only the preview artifact with the repository base path, configure Pages, upload the artifact, and deploy it. The workflow will use the currently supported official Pages action versions at implementation time rather than freezing an unverified version during planning. Permissions will be limited to contents read, Pages write, and the required OIDC/id-token permission. Pages settings and visibility remain human-owned prerequisites.

### 7. Make isolation and subpath checks first-class gates

Offline tests will inspect the preview import graph/source text and output for forbidden server/API/provider/secret references, verify that required asset URLs include the configured base path, and serve the artifact through a local static HTTP server. Rendered and browser acceptance will run against that static server at both desktop and 375px widths. No remote Supabase, provider, DNS, Cloudflare, or GitHub API access is required to verify the artifact locally.

## Risks / Trade-offs

- [Static host has no dynamic route fallback] → Use hash routes and test direct refresh for every required demo surface under a repository subpath.
- [Existing components may pull Next or server dependencies transitively] → Maintain an explicit preview import allowlist and use small preview adapters/components when a component is not client-safe; fail the build/test instead of bundling server code.
- [Visual drift between preview and main storefront] → Reuse the existing token/CSS authority and pure visual primitives, add rendered comparison/regression checks, and prohibit a second global design system.
- [Stakeholders may mistake demo state for real business state] → Show the global `FRONTEND PREVIEW` notice, label every transaction/fulfillment state as demo, use placeholder Order Success data, and keep server features technically unreachable.
- [Repository visibility or Pages settings may block publication] → Record these as human prerequisites in the runbook; do not change visibility, custom domain, DNS, or Cloudflare settings automatically.
- [A future application refactor changes shared CSS or pure helpers] → Keep preview-specific fixtures/adapters explicit and run the static preview gates in the normal verification workflow.

## Migration Plan

There is no database or application-data migration. Apply adds an isolated preview entry, tests, documentation, and a manual workflow. Rollback is deleting or disabling the preview workflow and removing the preview-only files; the main vinext/Worker artifact and canonical runtime state remain unchanged.

## Open Questions

None that change the approved scope or architecture. The repository's Pages setting, visibility eligibility, final public repository URL, and action versions are deployment-time inputs to be verified by the responsible maintainer during Apply/deployment, not application-runtime decisions.
