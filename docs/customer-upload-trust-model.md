# Private Customer Upload Trust Model

## 1. Status and scope

This document records the current trust boundaries for private customer-upload
media. It describes implemented provider-neutral contracts, local/test behavior,
legacy compatibility, and explicit production stop gates. It does not activate
production uploads, choose an object-storage provider, create a bucket, or
define production retention values.

## 2. Private-media principle

Customer-upload media is **private customer content**. It is not:

- `ProductAsset`;
- public marketing or catalog media;
- SEO media or sitemap data;
- public catalog fixture content;
- permanent public media.

No permanent public customer-media URL is approved. A customer-upload receipt
must never be converted into a public ProductAsset, emitted by public catalog
APIs, added to a sitemap, used as SEO media, or copied into production Product
fixtures. Conversely, a ProductAsset is not an owner-scoped customer receipt.

The new customer-upload contract exposes an opaque receipt identity and safe
validated metadata only. Provider locators, credentials, buckets, object keys,
signed URLs, and permanent URLs remain server/provider concerns.

## 3. Trust boundaries

The current trust model has these distinct parties:

| Boundary | Trusted input | Not trusted or not exposed |
|---|---|---|
| Browser | Selected file, local draft state, opaque receipt returned by the server | Owner authority, price, field authority, storage locator, receipt ownership |
| Guest owner boundary | Server-verified signed context | Browser-generated owner IDs, receipt possession alone |
| Field authority | Server-resolved Product CustomizationField constraints | Browser-declared field rules or arbitrary upload limits |
| Image inspection | Server-decoded supported type, byte size, and dimensions | Browser MIME/name/size claims |
| Object store | Provider-neutral receipt ID and private bytes | Browser-visible provider locator |
| Receipt repository | Server-derived owned receipt metadata and lifecycle commands | Direct anonymous CRUD or generic lifecycle mutation |
| Preview access | Verified owner, owned active receipt, short-lived capability | Permanent URL, provider credential, object key |

The application constructs privileged receipt repositories and object-store
dependencies only after the applicable server-side ownership and request gates.
Receipt IDs identify a request target; they do not authorize it.

## 4. Guest draft ownership

Guest customization does not require Supabase Auth or account creation. The
server issues an unguessable draft-owner identity and carries its integrity-
protected context in the current server-managed cookie mechanism.

The current codec creates a random 32-byte owner identity and signs a canonical
versioned payload with HMAC-SHA-256. The context contains only the opaque owner
identity and server timestamps needed for verification. No owner ID is
generated by browser JavaScript, and the signing secret is server-only.

The intended cookie properties are:

- `HttpOnly`;
- `SameSite=Lax`;
- `Path=/`;
- bounded `Max-Age` from runtime configuration;
- `Secure` in production runtime mode.

This document intentionally contains no real cookie value, owner ID, signing
secret, HMAC key, or test secret.

### First visit and no cookie

No existing valid owner context is not automatically unauthorized. The current
upload HTTP flow may issue a new server-managed guest owner context for a
first-time shopper, continue with the verified newly issued owner identity, and
return a `Set-Cookie` header. The browser does not receive the owner identity
as application JSON or client authority.

The first-visit issuance is different from accepting a malformed, tampered, or
expired context. An invalid or expired context fails closed and does not get
silently replaced during that protected operation.

### Invalid owner context

Malformed, tampered, expired, or otherwise unverifiable contexts do not yield
an owner identity. Protected operations map these cases to a bounded
unavailable/not-found result before creating privileged repository or provider
dependencies. A verification source failure maps to a temporary failure.

The owner context is a server authorization input. It is never serialized into
client props, returned as receipt metadata, accepted in the multipart body, or
written to safe customer-input telemetry.

## 5. Receipt contract

`CustomerUploadReceipt` is the safe customer-facing representation. The actual
current fields are:

- `receiptId` — opaque server-side receipt identity;
- optional normalized `originalFilename` display metadata;
- authoritative `contentType` limited to JPEG, PNG, or WebP;
- authoritative positive `byteSize`;
- authoritative decoded `dimensions` (`width`, `height`);
- server-derived `createdAt`;
- server-derived `expiresAt`;
- server-controlled `lifecycle`.

`OwnedCustomerUploadReceipt` is the server-side extension of that shape with an
`ownerId`. It is parsed only after the server-side owner boundary has derived
the identity. `parseOwnedCustomerUploadReceipt` does not verify a cookie or
token by itself.

The browser-safe receipt does not contain or accept as authority:

- `ownerId`;
- bucket or object container;
- provider object key, storage key, or internal locator;
- signed provider URL or permanent public URL;
- provider credentials, secret, cookie, or token;
- order attachment or payment metadata.

### `receiptId` is not authorization

**Possessing a `receiptId` is not proof of ownership.** Every owner-scoped
read, replace, remove, preview, or attach operation verifies the server-managed
guest owner context and then performs an owner-scoped receipt lookup.

A known receipt belonging to another owner and an unknown receipt do not become
an object-existence oracle. Customer-facing owner-scoped access returns the
same coarse not-found behavior for both cases. The receipt ID is also not a
provider object locator; it may be mapped internally by a future adapter but
that mapping never becomes browser authority.

## 6. Authoritative upload metadata

Browser-declared filename, MIME type, and byte size are hints only. The upload
acceptance service runs server-side image inspection against the bytes and the
server-resolved image-field constraints. Inspection establishes:

- supported detected content type;
- bounded received byte size;
- decoded dimensions;
- safe normalized filename metadata, when present;
- deterministic quality warnings based only on configured recommendations.

The safe receipt and upload response use inspected metadata, not browser claims.
The current implementation does not perform image transformation, background
removal, face analysis, pose analysis, people counting, or production-artwork
generation.

## 7. Private object-store boundary

`CustomerUploadObjectStore` is the current provider-neutral private-object
port. Its operations are:

- `putPrivateObject`;
- `readPrivateObject`;
- `inspectPrivateObject`;
- `deletePrivateObject`.

An eventual provider adapter may map the opaque `receiptId` to an internal
private locator. That locator is never returned to the browser and is not a
domain-level authorization credential. No bucket name, binding name, key
format, or provider-specific type is approved by this task.

### Receipt repository is separate from object storage

`CustomerUploadReceiptRepository` persists and authorizes receipt metadata and
lifecycle transitions. `CustomerUploadObjectStore` holds private bytes. They
are separate resource boundaries:

- selecting an object-storage provider does not automatically persist receipt
  metadata;
- a provider adapter does not create the receipt repository or Phase C order
  snapshot;
- receipt persistence and object deletion can partially fail independently;
- production receipt-repository persistence is **NOT ACTIVATED**.

The current local fake combines receipt state and preview authorization for
deterministic tests, but that is test composition, not a production persistence
decision.

## 8. Upload acceptance flow

The provider-neutral application semantics are:

```text
same-origin/request checks
→ guest owner issuance or verification
→ authoritative Product field-constraint resolution
→ multipart/file shape checks
→ server image inspection
→ private object persistence
→ authoritative receipt metadata persistence
→ safe opaque receipt response
```

An upload is not accepted merely because browser preflight passed or an object
provider put returned success. The acceptance service returns an accepted
receipt only after the inspected bytes are stored and the authoritative receipt
metadata repository returns a matching accepted record.

The actual production route is intentionally not composed with those
dependencies: `/api/uploads` currently resolves field constraints as a source
failure and the production provider dependencies are not configured. It
returns `503 Customer upload is temporarily unavailable.` rather than faking
success. The route's provider-neutral handler is exercised through injected
offline dependencies only.

## 9. Partial failure and compensation

Object storage and receipt metadata do not form a distributed ACID transaction.
The current acceptance service uses bounded compensation:

1. If authoritative image inspection or receipt construction fails, no object
   is accepted.
2. If the object write returns a failure before storage is known to exist, no
   receipt is accepted and no compensation is claimed.
3. If the object write succeeds but receipt metadata persistence fails, the
   service returns a source failure and attempts to delete the stored private
   object.
4. If that compensation succeeds, the failure remains non-accepted.
5. If compensation fails, the failure remains non-accepted and the private
   orphan boundary is recorded as an operational concern; it is not reported
   as a successful upload.

The service also treats repository throws and malformed persisted receipt data
as failure. It never turns partial resource state into a customer-visible
accepted receipt.

### Known orphan-object boundary

An object-provider write can succeed while connection/result handling fails
before a durable receipt exists. In that case the application may not be able
to know that the object was written and cannot safely claim a complete
compensation. A private orphan object is therefore a known Task 5.5/6.2
operational boundary.

Automatic provider-side orphan reconciliation is **NOT IMPLEMENTED**. No
scheduler, queue, cron job, or deployment timer is invented by this document.
Future provider/deployment work must define a safe reconciliation approach
without exposing private locators.

## 10. Receipt lifecycle

The current Phase B lifecycle vocabulary is exactly:

```text
active
replaced
removed
expired
cleanup_pending
cleanup_failed
cleanup_completed
```

There is no current `attached` lifecycle state in the Phase B domain contract.
Attachment is a separate reserved boundary.

### Legal transitions

The current explicit transition function allows:

```text
active → replaced | removed | expired
replaced | removed | expired | cleanup_failed → cleanup_pending
cleanup_pending → cleanup_completed | cleanup_failed
```

There is no generic browser or administrator `setLifecycle(...)` authority.
Equivalent safe retries are implemented by explicit command semantics rather
than arbitrary state updates.

### Replace

An owned eligible active receipt may be replaced by a distinct newly accepted
receipt owned by the same guest context. The old receipt becomes `replaced`; it
is not eagerly deleted. The replacement relationship is server-owned.

An equivalent retry of an already-applied replacement may replay safely. A
different replacement target for the same already-replaced receipt fails
closed. The new receipt is not automatically order-attached.

### Remove

An owned eligible active receipt may be changed to `removed`. Removal makes the
temporary content cleanup-eligible; it does not mean that private bytes have
already been physically deleted.

Repeated equivalent removal is safe and returns the same inactive outcome.
Attached content is protected by the future attachment-aware boundary. The
current Phase B command does not eagerly delete private bytes.

### Expiry

`expiresAt` is a server-derived receipt fact. Expiry is evaluated against an
explicit server-observed time and applies to eligible unattached active
content. Production retention duration is **UNRESOLVED**.

The following are not interchangeable:

- receipt expiry;
- guest owner-cookie lifetime;
- temporary preview capability TTL;
- provider signed-link lifetime;
- production media retention.

No fixture timestamp, test TTL, cookie TTL, or local preview value is a
production retention policy.

## 11. Cleanup lease and retry

Cleanup is not a read-list-then-delete operation. The provider-neutral
repository contract is:

```text
eligible receipt
→ atomic cleanup claim
→ cleanup_pending
→ private object deletion
→ cleanup_completed | cleanup_failed
```

The atomic claim is the concurrency barrier. Once `cleanup_pending` wins,
attachment cannot win through the same repository contract. Conversely, a
successful attach-once operation must prevent later cleanup of that receipt.

Current cleanup-eligible states are `replaced`, `removed`, `expired`, and
`cleanup_failed`. Active content, cleanup-pending content, completed cleanup,
and attached content are not ordinary cleanup candidates.

After provider deletion, the receipt transitions to `cleanup_completed`. If
deletion fails, it transitions to `cleanup_failed`, which remains retry-eligible.
An internally already-absent object may be treated as successful physical
absence by the adopted cleanup policy; the application does not expose that
provider detail to customers.

The deterministic in-memory repository and lifecycle service prove this claim-
before-delete shape locally. A durable production repository/transaction and a
production scheduler are not activated. The legacy administrator cleanup route
is a separate legacy/prototype path and is not evidence that the new
CustomerUpload cleanup scheduler exists.

## 12. Attach-once boundary

`attachOwnedReceiptOnce(...)` is a **reserved opaque attachment boundary**.
Its provider-neutral intended semantics are:

- the verified owner is required;
- the receipt must be active and eligible;
- a receipt in `cleanup_pending` cannot attach;
- the same target retry may replay safely;
- a different target fails closed;
- one receipt cannot be successfully attached to two different targets.

The current local fake stores only an opaque test attachment identity to prove
these command semantics. Attachment is not a current Phase B lifecycle state.

The current boundary does **not** durably persist:

- an `OrderItem` reference;
- `fieldId` or `fieldCode`;
- image position;
- crop metadata;
- `configurationRevision`;
- an immutable customization snapshot.

Task 8.5 remains **BLOCKED** because those Phase C facts must be attached to
the resulting order/customization boundary exactly once after the order item
exists, under the ordered C1 dependency. The future schema proposal's
`attached` state and immutable snapshot rows are **FUTURE / PHASE C PROPOSAL**,
not current runtime semantics.

## 13. Customer-input preview

The canonical term is **Customer input preview**. It is never a production
preview, manufacturing mockup, production proof, final artwork approval, or
guarantee of production framing.

### Browser-local preview

Before or around upload, the browser may create a temporary revocable object
URL for the selected `File`. The current local preview helper revokes the URL
on replacement or disposal. This behavior:

- does not upload bytes;
- does not create a receipt;
- does not publish media;
- does not create a ProductAsset;
- does not prove server acceptance;
- does not prove production rendering.

### Server-backed preview

The provider-neutral preview handler uses this order:

```text
owner context verification
→ owner-scoped receipt lookup
→ active/unexpired check
→ short-lived preview capability authorization
→ private object read
→ private no-store image response
```

The capability contains only an opaque `receiptId` and an `expiresAt` bounded
by the receipt expiry. The response uses `Cache-Control: private, no-store`
and does not return a provider URL, bucket, object key, credential, or
permanent public link.

The actual `/api/customer-uploads/preview` route currently returns `503
Customer input preview is temporarily unavailable.` because the production
provider and receipt persistence are not activated. The provider-neutral
handler and local fake are testable offline; this is not production preview
availability.

### Preview TTL

Production preview authorization TTL is **UNRESOLVED**. It is distinct from
receipt/media retention, `expiresAt`, guest owner-cookie lifetime, and any
provider signed-link lifetime. Test-only fake timestamps do not establish the
production value.

Known cross-owner and unknown receipt requests are intentionally mapped to
coarse unavailable/not-found behavior. They must not reveal whether an object
exists.

## 14. ProductAsset separation

| System | Purpose | Visibility | Authority |
|---|---|---|---|
| `ProductAsset` | Public catalog/marketing media | Publicly accessible reference metadata | Product/catalog administration |
| `CustomerUploadReceipt` | Shopper-provided personalization input | Private, owner-scoped temporary media | Server upload and receipt boundaries |
| Production preview | Future production workflow output | Not implemented | Future approved production workflow |
| Digital delivery file | Future/private order fulfillment output | Not implemented here | Future approved delivery workflow |

Customer uploads must not be converted to ProductAsset, returned by public
catalog APIs, added to sitemap/SEO output, copied into public fixture data, or
given permanent public URLs. ProductAsset metadata must not be used as an
owner-scoped receipt or as proof of customer-upload ownership.

## 15. Safe response, error, and log boundary

The new customer-upload HTTP and observability boundaries use closed safe
categories and safe issue/warning messages. They exclude from customer-facing
responses and safe telemetry:

- uploaded bytes;
- customer customization text;
- owner context, cookie, token, or owner ID;
- bucket/container and object key;
- provider locator or signed URL;
- credentials and secrets;
- SQL details or hints;
- raw provider errors;
- cross-customer object-existence detail.

An opaque `receiptId` may be returned for the shopper's accepted upload, but it
is not a provider locator and is not authorization. Unknown thrown values are
not inspected by the new safe observability boundary.

The existing legacy cleanup/order/photo paths may contain historical storage
keys, signed-link behavior, and prototype diagnostics. They remain isolated
legacy compatibility and are not approval evidence for the new private-media
trust model.

## 16. Local fixtures and fakes

The following are **LOCAL / TEST ONLY**:

- deterministic in-memory object store;
- deterministic in-memory receipt repository and preview access;
- finite failure controls for object write, metadata write, preview, read,
  delete, throw, and compensation cases;
- local customer-upload smoke harness;
- explicit development CustomizationField fixtures.

They are deterministic and offline. They are not:

- production provider approval;
- a production bucket or binding;
- a retention policy;
- durability, scaling, cost, regional-residency, or deployment evidence;
- a business-approved customer-data policy;
- production customer data.

Production source failure must not fall back to these fakes or fixtures. The
local smoke harness composes explicit fixture field authority with in-memory
resources and verifies owner-scoped receipt and byte round-trip behavior. It
does not contact Supabase Storage, Cloudflare R2, remote Supabase, or another
live service.
